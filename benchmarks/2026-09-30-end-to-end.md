# End-to-end search latency — 2026-09-30

Optimized release builds on Xenia, dev MacBook, and personal MacBook. Baseline:
41f2204. The updated build reuses shared HTTP connections and retains one idle
local embedding/reranking backend between searches. Node identities and tokens
remain request-specific. Installed model files are checked on every search;
changing their timestamps or the installation marker invalidates model reuse.

## Persistent MCP results

Times include JSON-RPC request/response, actual local MiniLM 384-dimensional
query embedding, SQLite FTS5 and exact cosine retrieval, and local Jina reranking
of up to ten candidates. Merged searches also include authenticated HTTP access
to Redis on Xenia and fusion with other nodes' results.

| Machine | Local median before | Local median after | Local p95 after | Merged median before | Merged median after | Merged p95 after |
|---|---:|---:|---:|---:|---:|---:|
| Dev MacBook | 218.53 ms | 61.13 ms | 70.47 ms | 887.24 ms | 209.21 ms | 249.45 ms |
| Personal MacBook | 243.98 ms | 49.46 ms | 57.87 ms | 895.99 ms | 191.60 ms | 208.66 ms |
| Xenia | 426.35 ms | 61.52 ms | 96.86 ms | 480.28 ms | 75.18 ms | 148.79 ms |

The first merged call in a new MCP process still paid model/connection startup:
875.91 ms on dev MacBook, 935.05 ms on personal MacBook, and 614.63 ms on Xenia.
Subsequent local searches use the same loaded models, without caching results.

## Connection reuse

On the same 3,000-message fixture, an API-only diagnostic returned approximately
108–110 KB of candidates and document projections. Ten measured requests per
mode, after two warmups, gave these medians:

| Machine | Fresh HTTP connection | Reused HTTP connection |
|---|---:|---:|
| Dev MacBook | 629.16 ms | 134.06 ms |
| Personal MacBook | 599.96 ms | 130.07 ms |

An intermediate build with only HTTP reuse measured merged MCP medians of

This diagnostic isolates a substantial network/connection contribution; it
does not measure Axum overhead separately.

## CLI and limits

Each standalone CLI invocation starts a new process, so it cannot retain the
previous process's model or HTTP connection. Updated CLI medians were:

| Machine | Local CLI | Merged CLI |
|---|---:|---:|
| Dev MacBook | 271.96 ms | 916.06 ms |
| Personal MacBook | 338.08 ms | 954.61 ms |
| Xenia | 551.05 ms | 547.76 ms |

All runs used 1,000 deterministic synthetic messages per node, 3,000 in the
shared group, and five rotating queries. Each node issued sequential calls;
the three nodes ran concurrently. Each scenario measured ten CLI invocations
and twenty MCP calls after excluding its first call. Local followed merged in
the same MCP process, so both measured MCP scenarios had loaded models. There
were no search failures or shared-index fallbacks.

The disposable Redis instance had four CPU cores, a 4 GiB container limit, AOF
persistence, and exact FLAT retrieval. The service and histories were separate
from production. These were short successive runs on shared machines, not a
controlled full-history benchmark. Corpus size, document length, machine load,
and network conditions affect latency. No approximate SQLite index was added:
SQLite stores quantized vectors and Rust performs exact cosine scans in chunks.

`/home/james/scratch/mash-perf-20260930/e2e-http-pool` (updated runs).

## On-demand CLI worker

A subsequent build adds a private per-user CLI search worker that exits after
60 seconds without requests. The same fixture and five rotating queries now
give these end-to-end CLI timings:

| Machine | Direct local median (`--no-worker`) | Warm worker local median | Warm worker local p95 | Warm worker merged median | Warm worker merged p95 |
|---|---:|---:|---:|---:|---:|
| Dev MacBook | 258.61 ms | 66.70 ms | 90.56 ms | 216.83 ms | 235.54 ms |
| Personal MacBook | 358.73 ms | 66.56 ms | 87.02 ms | 199.49 ms | 235.41 ms |
| Xenia | 460.47 ms | 57.19 ms | 95.02 ms | 60.79 ms | 71.32 ms |

There were twenty measured commands per worker scenario, excluding the first
call, and ten direct invocations per scenario. The first local command,
including launching the worker, took 906.49 ms on dev MacBook, 1,057.81 ms on
personal MacBook, and 446.89 ms on Xenia. The first subsequent merged command
also needed a fresh remote HTTP connection on the MacBooks, taking roughly
706–710 ms; later calls reused it.

Four concurrent searches from separate CLI processes were also checked on
Xenia. They started one worker, returned the same results as direct execution
for four different queries, and preserved typed error exit codes. The default
idle shutdown was observed separately. The worker stores models and connection
pools, not query results, and reads configuration and SQLite data per request.
MCP remains an independent process with its own model cache.

The same small-corpus and machine-load limits above apply. No production history
was indexed for this benchmark. Artifacts are retained at
`/home/james/scratch/mash-perf-20260930/e2e-cli-worker`.
